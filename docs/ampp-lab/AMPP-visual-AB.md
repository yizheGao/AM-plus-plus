# 动态背景双方案（mod33）· 交付说明

> 2026-11-13 夜 ｜ 设备：Redmi Pad 26048RP6AC / Apple Music 7.0.0(1614)
> 参考对象：平板上安装的 LyricsBlossom 8.1（包名 `com.lyricsblossom.app`）

## 0. 一句话

方案 A 按参考软件的做法还原（封面派生网格渐变，安静、几乎不闪）；
方案 B 是自研的"极光幕帘"（竖直光幕缓慢漂移）。
两者是两条独立的绘制路径，在「设置 → 歌词效果 → 极光风格（方案 B）」一键切换，默认 A。

## 1. 对参考软件的实际观察（不是猜的）

在平板上直接运行 LyricsBlossom、授予 MediaProjection（共享 Apple Music）后逐帧采样：

| 观察项 | 实测 |
|---|---|
| 背景构成 | 一层由封面派生的平滑色场，几乎无纹理；封面/控件/歌词浮在上面 |
| 颜色 | 单一主色相为主（蓝封面→蓝场），空间变化很小；亮度中位 ~75/255 |
| 运动 | 极缓；帧间平均差 4–9/255（间隔约 4.6 s），无局部闪烁、无粒子 |
| 变化分布 | 时域方差在四角/边缘最大（9–13），画面中心最小——是整场的缓慢起伏，不是点状光效 |
| 明暗 | 底部/边角更暗（暗角），中部最亮；有 4×4 级 ordered dither 去色带 |
| 与我方旧实现的差别 | 旧版是"边缘光环 + 换行脉冲"，形状硬、能量尖，观感突兀 |

二进制侧（`analysis/lyricsblossom/REPORT.md`）：背景 = `BackdropMeshLayer`（≤24×24 网格）
+ `GradientCS` 从封面纹理算色 + `Backdrop.BroadBlur` 兜底 + `OrderedDitherEffect`；
**没有**粒子/bloom/反馈/频谱/beat 检测；音频只有 6 个平滑频带 + 4 个标量在缓慢改色。

## 2. 方案 A：封面网格（还原）

| 项 | 实现 |
|---|---|
| 采样 | 96×96 封面副本，按格**面积平均**（不是点采样，避免单个色块污染整格） |
| 主色 | 按饱和度加权求整张封面的主色，每格向主色混合 **0.62** → 得到单色相为主的场 |
| 网格 | 11×8（设置「柔光范围」控制 4–20 列） |
| 放大 | 小位图 `drawBitmap(FILTER_BITMAP)` 双线性铺满，天然就是网格插值 |
| 明度 | 压到 **0.20–0.46**，保证歌词可读、贴近参考的暗底 |
| 运动 | 每格独立相位慢漂移；**能量只 +6%**（旧版 +22%，这是"闪"的根源） |
| 去带 | 4×4 Bayer + `PLUS` 0–4 级 |
| 帧率 | 静止 8 fps、有能量 20 fps |

## 3. 方案 B：极光幕帘（自研）

| 项 | 实现 |
|---|---|
| 形体 | 3 条沿正弦中心线铺开的光带，跨整屏画弧 |
| 柔边 | 预生成 96×160 掩码（横向钟形 × 纵向 smoothstep），`SRC_IN` 上色 → 双轴柔边，无硬边 |
| 运动 | 中心线的基准高度(0.13)、振幅(0.09)、频率(0.07)、横向漂移(0.11)、行进亮带(0.37) 各用不同速率，整条带在屏幕上游走 |
| 叠加 | `BlendMode.PLUS`，每采样点共用单位半径径向渐变（canvas 变换缩放，无每帧分配），alpha 上限 0.30 |
| 与 A 的关系 | A 的底色仍在下面；B 是叠加层。但它有独立的形体/运动/能量映射，不是 A 的参数变体 |

## 6. 失败与未解决

1. **主界面底部色带（本次唯一未修项）**：这一条做了对照实验——
   - 折叠态防绘制补丁**前后**截同一位置：色带像素 `69.3,105.3,144.8` vs `69.3,105.0,147.3`，
     逐像素几乎完全相同 → 不是我们的光效层画的；
   - 视图树 dump：`player_sheet_container` / `mini_player` 背景都是 `null`，模块没有给它们上过背景；
   - 唯一覆盖该区域的宿主元素是 `player_coordinator`（`ColorDrawable`）与 `top_and_bottom_gradients`（Compose 渐变）。
   **结论：宿主自己的 mini player 材质**，模块侧无写入点。没有擅自改动宿主材质——需要你确认具体现象
   （是"整条色带"，还是"封面被切一半"，还是别的），我再做针对性覆盖。
2. LyricsBlossom 的 52 个 shader 是 AES-256-GCM 加密的，密钥推导差最后一步变换（详见 REPORT §3.3），
   所以方案 A 是"行为复刻"而非"代码复刻"。
3. 参考软件的真·动态封面（Apple motion artwork）需要 Apple 令牌，未使用。
4. 逐词事件驱动在无歌词曲目上退化为仅换行，密度会明显下降。

## 6.6 方案 A 已按参考统计调参（mod34，离线仿真驱动）

对参考帧与我们的帧做同口径背景统计（剔除封面/控件/底栏）：

| | 平均亮度 | p90 | 饱和度 |
|---|---|---|---|
| 参考（LyricsBlossom 播放中） | 81.1 | 93.7 | 0.39 |
| 我们（mod33） | 95.9 | 150.7 | 0.31 |
| 我们（mod34，仿真） | 75.7 | 82.0 | 0.37 |

问题很清楚：mod33 偏亮、动态范围过大（p90 150 说明有大片浅色）、偏灰。

改动（`GlowLayer.kt`）：主色混合 0.62→**0.75**、明度下限 0.20→**0.25**、饱和度 **×1.3**、
色相漂移 ±1.4°→**±7.7°**、新增**径向压暗 0.18**（复刻参考的角部更暗）。

离线渲染对照图：`/tmp/preview_ab.png`（上=mod33，下=mod34）。
**状态：已编译、已出包，未安装**——平板锁屏无法验证，设备上仍是已验证的 mod33。

## 6.6.1 底部色带：再补一条色彩证据

| 采样 | RGB |
|---|---|
| 底部色带（x<534 区域） | `69, 105, 145` |
| 迷你播放器缩略图（同一帧） | `186, 192, 198` |
| 比值 | `0.37 / 0.55 / 0.73` |

色带不是"缩略图压暗"（比例不一致），而是**更高饱和度的蓝**——与 Apple 的"正在播放材质色"一致，
属于宿主为 mini player 生成的主题材质，不是我们图层或模块写入（模块侧两条对照：像素级前后对比不变、
视图树里 `player_sheet_container`/`mini_player` 背景均为 null）。

## 6.6.2 底部色带：结论修正 —— 是我们自己的层（已修复）

前一版判断"宿主 Compose 材质"是**错的**。决定性实验：把「词曲光效」设为"关闭"后，
主界面底部立刻变回页面底色（纯白/深色），色带消失 → 色带来自我们的 `GlowView`。

为什么之前看不出来：折叠态下 `player_root` / `GlowView` 仍然保持**全尺寸**（3008×1880），
只是被 `player_sheet_container` 裁剪成 mini player 那条 180px。所以：
- 按"自身高度"判断 → 永远判成展开；
- 按"root 高度"判断 → 同样无效；
- 逐个把候选 View alpha 置 0 的探针，命中的是另一个 activity 的实例。

修复（mod37）：`onDraw` 里用 `getGlobalVisibleRect()` 的实际可见高度判断，
可见高度 < 自身 35% 直接不画。实测：

| 状态 | 底部像素 |
|---|---|
| 折叠（资料库页，浅色） | `255,255,255` 页面底色，胶囊悬浮 |
| 折叠（深色专辑页） | 页面自身的深紫，胶囊悬浮 |
| 展开（播放页） | 正常渐变（`15,1,53`） |
